1. MVVM (Model–View–ViewModel) penting karena membantu memisahkan tanggung jawab setiap bagian aplikasi sehingga kode lebih rapi, mudah dipahami, mudah diuji, dan gampang dikembangkan. Dengan MVVM, UI tidak langsung berurusan dengan data atau logika bisnis, melainkan lewat ViewModel. Ini mengurangi ketergantungan (tight coupling) antara tampilan dan logika aplikasi.

Model berisi data dan struktur respons API, yaitu Movie, PopularMoviesResponse, serta lapisan data seperti MovieRepository dan MovieService (API).
View adalah bagian yang menampilkan UI dan menerima interaksi pengguna, yaitu MainActivity, DetailsActivity, file XML layout (activity_main.xml, view_movie_item.xml, dll), serta MovieAdapter.
ViewModel adalah penghubung antara View dan Model yang menyiapkan data agar siap ditampilkan, yaitu MovieViewModel. ViewModel ini bertugas mengambil data dari MovieRepository dan menyimpannya dalam StateFlow tanpa mengetahui detail UI.

2. Data Binding lebih efisien karena menghubungkan data langsung ke UI secara deklaratif melalui XML, tanpa perlu banyak kode boilerplate di Activity atau Fragment. Dengan Data Binding, UI akan otomatis ter-update saat data berubah, selama masih dalam lifecycle yang aktif. Hal ini mengurangi pemanggilan findViewById, menghindari kesalahan sinkronisasi antara data dan tampilan, serta membuat Activity lebih bersih karena fokus pada logika navigasi, bukan mengatur tampilan satu per satu. Selain itu, Data Binding bekerja sangat baik dengan MVVM karena View cukup “mengamati” data dari ViewModel, tanpa harus tahu bagaimana data tersebut diproses atau diperoleh.

3. Singleton Pattern itu penting karena memastikan hanya ada satu instance dari suatu objek yang dipakai bersama di seluruh aplikasi, khususnya untuk komponen yang bersifat mahal dan sensitif terhadap resource seperti Room Database. Pada kasus ini, MovieDatabase dibuat sebagai singleton agar tidak terjadi pembuatan banyak instance database yang bisa menyebabkan race condition, inkonsistensi data, pemborosan memori, dan error saat akses data secara bersamaan dari banyak thread. Dengan satu instance yang dikelola secara terpusat, setiap bagian aplikasi (Repository, ViewModel, dll.) selalu mengakses sumber data yang sama, sehingga data tetap sinkron dan aman. Selain itu, Singleton juga meningkatkan efisiensi performa karena proses inisialisasi database hanya dilakukan sekali selama aplikasi berjalan, bukan berulang-ulang setiap kali dibutuhkan.

4. Repository Pattern itu penting karena berfungsi sebagai lapisan perantara (abstraction layer) antara sumber data dan bagian aplikasi lain seperti ViewModel atau Worker, sehingga detail dari mana dan bagaimana data diambil tidak diketahui oleh layer di atasnya. Pada implementasi kamu, MovieRepository menyatukan dua sumber data yang berbeda, yaitu network (Retrofit API) dan local database (Room), lalu menyediakan satu cara yang konsisten untuk mengakses data tersebut.

Dengan Repository Pattern, ViewModel dan Worker tidak perlu tahu apakah data berasal dari API, database lokal, atau dari mekanisme refresh berkala menggunakan WorkManager. Mereka cukup memanggil fungsi repository, sehingga kode menjadi lebih bersih, terstruktur, dan mudah diuji. Selain itu, Repository memungkinkan pengelolaan strategi data seperti cache-first (ambil dari database jika ada, jika tidak baru dari network), sinkronisasi data secara berkala, serta penanganan error di satu tempat saja. Hal ini meningkatkan maintainability, memudahkan skalabilitas aplikasi, dan membuat perubahan sumber data di masa depan bisa dilakukan tanpa memengaruhi layer UI.

5. Ya, ada beberapa cara lain untuk memperbarui database selain menggunakan WorkManager.

Pertama, kamu bisa melakukan refresh data saat aplikasi dijalankan atau saat UI aktif. Misalnya di ViewModel, kamu memicu pemanggilan API setiap kali MainActivity dibuka atau menggunakan repeatOnLifecycle agar data diperbarui ketika app berada di state STARTED atau RESUMED. Cara ini cocok jika data hanya perlu up-to-date saat user benar-benar menggunakan aplikasi, tapi tidak berjalan ketika aplikasi ditutup.

Kedua, kamu bisa menggunakan foreground service untuk melakukan sinkronisasi data secara berkala dalam waktu tertentu. Foreground service berjalan dengan notifikasi aktif, sehingga sistem tidak mudah mematikan prosesnya. Namun, pendekatan ini lebih berat, boros baterai, dan kurang direkomendasikan hanya untuk refresh data biasa.

Ketiga, kamu dapat memanfaatkan push mechanism dari server, seperti Firebase Cloud Messaging (FCM). Server bisa mengirim notifikasi “data updated”, lalu aplikasi merespons dengan mengambil data terbaru dan menyimpannya ke database. Ini sangat efisien karena refresh hanya terjadi saat ada perubahan, tetapi membutuhkan infrastruktur backend tambahan.

Keempat, refresh data juga bisa dilakukan secara manual atau berdasarkan user action, misalnya dengan fitur pull-to-refresh. Saat user menarik layar ke bawah, aplikasi memanggil API lalu memperbarui database lokal. Pendekatan ini simpel, user-controlled, dan sering dipakai, tetapi tentu tidak otomatis.

Dibandingkan semua alternatif tersebut, WorkManager adalah pilihan paling stabil untuk background refresh jangka panjang karena dijamin tetap berjalan meskipun aplikasi ditutup atau device di-restart, serta mematuhi kebijakan sistem Android terkait baterai dan background execution.
